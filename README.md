# 机格分裂 Machine Persona

一个围绕现成大语言模型构建的上下文感知交互系统。不训练新模型，而是在模型外部加一层判断——在回应用户之前，先判断当前该用哪种"机格"（模式）、要不要主动介入、介入到什么程度，尽量做到**在正确的时间，以正确的方式，做正确程度的事情。**

## 起点

这个项目最初的动机很简单：觉得现有的 AI 助手不够好用。深入想下去后发现，问题往往不是模型能力不够，而是它在错误的时机介入——理解了用户的目标，却没检查这个目标背后需要的前置条件是否成立；用户还在发散阶段，它已经开始收敛；用户只是想被接住情绪，它却把每句话都当成一个待办任务处理。

这个项目想解决的不是"让 AI 更聪明"，而是"让 AI 知道现在该做什么、不该做什么"。

## 五个机格

系统把交互场景拆分成五种模式，每一种对应一套不同的行为准则：

**闲聊机格** —— 处理日常聊天、吐槽、轻情绪表达、没有明确任务诉求的交流。接住话题就好，不强迫产出，不把每句话都强行升级成一个项目或待办事项。

**Brainstorming 机格** —— 处理新点子、模糊想法、还没成形的方向。优先沿着用户原本的思路扩展、建立连接，不过早列风险、竞品、可行性问题，那些等用户明确要收敛时再说。

**写作机格** —— 处理论文、简历、邮件、文档、代码解释这类文字工作。先诊断真正需要改的地方，保留用户已经确定的部分，倾向于做最小但高价值的修改，而不是擅自重写整体逻辑。

**协作执行机格** —— 处理需要多个步骤、依赖前置材料或条件才能推进的任务。核心动作是识别目标、识别当前进行到哪一步、检查真正阻塞下一步的前提条件，只问一个必要的问题，给出具体可执行的下一步，不跳步、不空问、不一次性甩出整套方案。

**判断机格** —— 处理"哪个更好""该不该做""这个可行吗"这类问题。检查隐藏前提、给出明确结论，并说明什么条件会让结论改变，不为了显得中立而回避表态。

**Repair（覆盖状态）** —— 不是第六个机格，而是贯穿所有模式的异常处理。当用户表达出"不是这个意思""你理解错了"这类偏航信号时，先停下当前方向，说清楚偏差在哪，再做最小修正，然后回到正确的模式继续。

## 每个机格怎么处理对话

判断流程统一是：先读取当前对话内容和已知的上下文信号，判断该走哪个机格、要不要介入、介入多深，再按对应机格的行为准则生成回答。

以协作执行机格为例：用户说"我要整理实习 JD"，系统不会默认这句话意味着用户已经有数据、可以直接开始生成表格。它会先检查这个任务真正需要的前提条件是否成立——用户手头有没有 JD 数据源——如果没有，只问这一个真正阻塞下一步的问题，而不是先把一整套字段设计和分类标准摆出来。这个原则贯穿所有机格：**先确认前提，再决定要不要展开，展开多少。**

## 项目定位：1.0 / MVP

这是这套设计的最小可行版本，目标是先跑通一条最短闭环——对话进来、判断该走哪个机格、生成对应回答、把判断过程展示出来——而不是一次性把系统做全。

第一版有意保持简单：单一模型调用、没有复杂的多轮循环和工具编排，判断逻辑用普通的 Python Pipeline 实现。这些取舍是刻意的，不是能力不够——等系统本身的状态、分支、工具调用变复杂到普通 Pipeline 撑不住的时候，再考虑更复杂的编排方案，而不是一开始就为了还不存在的复杂度去搭一套过重的架构。

2.0 会在这个基础上继续更新，包括更完整的工作流状态管理、更多机格边界的打磨，以及把已经验证过的 Skill 版本判断逻辑，迁移成一个真正独立运行的系统。

## 已验证的原型

在写完整套系统之前，先把核心的判断逻辑（尤其是协作执行机格里的前置条件检查）做成了一个可以直接安装使用的 Skill，在真实场景里测试、发现问题、修复，记录了完整的迭代过程。
